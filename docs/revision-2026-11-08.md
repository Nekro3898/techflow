# Correcciones verificadas — 8 de noviembre de 2026

## Alcance

Se conservaron los archivos, las funciones existentes, las rutas y el diseño de
la interfaz. Se añadieron auxiliares internos en los mismos módulos para compartir
validaciones y evitar duplicar lógica. No se cambiaron las tablas de negocio ni
se agregaron pantallas. Las funciones disponibles solo por API siguen disponibles
por API; esta revisión no incorpora login, roles ni nuevos módulos.

## Correcciones

- Resumen: identificadores correctos, últimas ventas de hoy, unidades vendidas,
  saldo real y estado del servidor. El enlace Ver todo activa la pestaña de ventas.
- Pagos: escribir no recrea el input enfocado. Se comparan centavos y se explican
  diferencias de pago y efectivo. El comprobante permanece tras actualizar el POS.
- Reintentos: solicitud persistida antes de enviar, bloqueo mientras su resultado
  es incierto y reenvío idéntico después de una recarga. El servidor devuelve la
  misma venta y el mismo vuelto sin descontar stock otra vez.
- Concurrencia: un cerrojo por base adquirido antes de las escrituras, junto con
  transacciones y bloqueo de filas, coordina venta, apertura, cierre, stock y edición.
  La elección serializa escrituras: es deliberada para una tienda pequeña y no
  está pensada para un sistema de alta concurrencia. Las lecturas no toman ese cerrojo.
- Anulaciones: restituyen stock y generan un retiro por el efectivo a devolver,
  preservando el asiento original. Se rechazan si la caja original está cerrada.
- Stock: cantidades enteras, agrupación de variantes repetidas y ajustes con
  dirección y stocks anterior/posterior. Se sugieren IDs de variantes en el mismo campo.
- Validación: objetos/listas, números finitos, límites, nombres, importes finales,
  booleanos, fechas y rangos. Cerrar requiere enviar efectivo_contado.
- PATCH: actualiza únicamente los campos enviados y distingue ausencia del recurso
  de una actualización sin cambios. El producto incluye proveedor_id al consultarlo.
- Seguridad de presentación: los datos se escapan antes de insertarse en HTML;
  las insignias conservan su aspecto mediante marcado interno controlado.
- Fechas: sesión SQL UTC-03, JSON ISO 8601 con zona y filtros de calendario local.
- Recursos: cierre de conexiones incluso si falla el cursor; errores JSON y límite
  de cuerpo de solicitud. Depurador desactivado en el lanzador normal.
- Instalación: SQL inicial sin DROP y con detección de base existente; npm start
  inicia Flask. Documentación actualizada y demo con usuario de aplicación.

## Reparación del entorno XAMPP

El usuario techflow_app autenticaba, pero carecía de permisos sobre techflow. GRANT
provocaba una caída interna de MariaDB 10.4.32. CHECK TABLE daba OK; las reparaciones
online/offline de índices no resolvieron el fallo. Reconstruir mysql.db con
ALTER TABLE mysql.db ENGINE=Aria permitió aplicar los permisos previstos y usar
la aplicación normal. No se cambiaron contraseñas ni permisos globales.

Antes de intervenir se guardaron respaldos SQL y físicos en
`C:\Users\ezequ\AppData\Local\TechFlow\backups`. Se conservan fuera del repositorio.

https://mariadb.com/docs/server/clients-and-utilities/aria-clients-and-utilities/aria_chk

## Límites

Las correcciones no reconstruyen información ya perdida por el código antiguo:
por ejemplo, el signo de ajustes históricos o importes anulados que ya fueron
puestos en cero. No se migraron esos registros por inferencia. Se mantiene el uso
local y la estructura original; no se garantiza ausencia absoluta de defectos ni
se presenta este proyecto académico como un despliegue público listo para producción.
